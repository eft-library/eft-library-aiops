# 일일 → 주간 → 월간 분석

이 문서가 정기 분석 기간·입력·버전의 기준이다. 직접 run과 SQLite 저장 설명은 AIOPS_DATABASE_URL을 설정하지 않은 로컬 모드 기준이다. PostgreSQL 모드의 큐·Worker·저장·이력 이전은 [POSTGRES_WORKER.md](POSTGRES_WORKER.md)를 따른다. 수집 배치는 실행 단위, 보고서는 한국 시간 달력 기간 단위이며 둘을 구분한다. 기존 증분 체크포인트는 그대로 사용한다.

## 기간과 의존 관계

모든 구간은 **Asia/Seoul, 시작 포함·끝 제외**다.

| 유형 | 범위 | 기본 입력 | 예정 실행 |
|---|---|---|---|
| daily | 전날 00:00부터 오늘 00:00 직전 | 그 날짜의 로그 이벤트·시스템 지표 | 매일 자정 이후 |
| weekly | 지난 월요일 00:00부터 이번 월요일 00:00 직전 | 해당 날짜의 최신 유효 일일 보고서 7개 | 매주 월요일 |
| monthly | 지난달 1일 00:00부터 이번 달 1일 00:00 직전 | 지난달의 최신 유효 일일 보고서 전체 | 매월 1일 |

월간의 주간 보고서는 **보조 문맥**이다. 월 경계에 걸친 주간 보고서가 있더라도 일일 결과에 그 수치를 다시 더하지 않는다. 원본 로그 전체를 주·월마다 재전송하지 않는다. 각 일일 보고서의 AI 요약과 함께 코드가 계산한 관측 이벤트·오류·HTTP 건수를 전달하고, 주·월 관측 합계는 일일 보고서에서만 계산한다. 누락 날짜를 0건으로 간주해 완전한 기간 합계처럼 표현하지 않는다.

명시적 `--date`는 daily의 해당 날짜, weekly의 그 날짜가 속한 월요일 시작 주, monthly의 그 날짜가 속한 달을 선택한다. 생략하면 실행 시점의 마지막 종료된 기간을 선택한다. 아직 끝나지 않은 기간은 거부한다. 월 길이·윤년·연말을 달력 기준으로 계산한다.

## 수집과 분석 분리

수집은 짧은 주기, 예를 들어 5분마다 호스트에서 `collect`를 실행한다. 기본 보고서 커버리지 기대값도 5분이다. 이는 **분석 준비의 기본 가정이며 자동 스케줄이 설치되었다는 뜻은 아니다.** 실제 주기를 바꾸면 `--interval-minutes`도 동일하게 설정한다.

```sh
uv run aiops --env-file .env collect --config config/log_sources.yaml --all
```

일일 분석용 정상 수집에는 `--since`를 붙이지 않는다. `--since`는 수집 시 레코드를 제외하므로 이미 사라진 과거 로그를 나중에 복원해 주지 않는다. 새 배치는 제외된 로그의 날짜별 건수도 기록해 해당 일자의 입력이 불완전함을 표시한다. 필터 제외 건수는 원문을 보관하는 기능이 아니다.

자원 지표는 수집 시점에 관측한 샘플이다. 서버를 하루 한 번만 수집했다고 과거 24시간 CPU/RAM 이력이 생기는 것은 아니다.

## 명령

`prepare`는 날짜별 입력·근거 목록을 준비하고 **Codex를 실행하지 않는다**. `run`은 같은 준비 단계를 수행한 뒤 **실제 Codex를 실행하고 결과를 저장**한다. 둘 중 실행 목적에 맞게 선택하며, prepare 후 확인하고 run해도 된다.

```sh
# 기본 날짜: 전날. 운영 소스 목록을 기준으로 누락 확인
uv run aiops --env-file .env report prepare --type daily --config config/log_sources.yaml

# 준비 결과를 확인한 뒤 실제 일일 분석
uv run aiops --env-file .env report run --type daily --config config/log_sources.yaml

# 특정 날짜를 선택하는 예
uv run aiops --env-file .env report prepare --type daily --date 2026-10-27 --config config/log_sources.yaml
uv run aiops --env-file .env report run --type daily --date 2026-10-27 --config config/log_sources.yaml

# 마지막 종료된 주와 월: 관련 일일 보고서를 먼저 완료해야 함
uv run aiops --env-file .env report run --type weekly
uv run aiops --env-file .env report run --type monthly

# 이력과 갱신 필요 여부
uv run aiops --env-file .env report list
uv run aiops --env-file .env report list --type daily
```

`.env`를 사용하지 않으면 `--env-file .env`만 생략한다. `--config`는 daily의 기대 서비스 목록을 정하며 기본값은 fixture 프로필이므로 **운영 daily에서는 반드시 운영 프로필을 지정**한다. 주간·월간은 완료된 일일 보고서를 참조하므로 해당 옵션을 따로 지정할 필요가 없다.

`--interval-minutes 10`처럼 실제 수집 주기를 지정할 수 있다. 1~1440분을 허용한다. 일일 입력은 서비스별로 기대 시간 슬롯 중 수집 성공이 관측된 슬롯을 계산한다. 슬롯이 모두 채워져도 로그 손실이 절대 없다는 보증은 아니다.

## 일일 데이터 구성과 지연 도착

- 모든 `events.jsonl`의 레코드를 스트리밍 집계한다. 배치의 대표 로그만 들어 있는 `snapshot.json`을 합산하지 않는다.
- 로그는 **이벤트 시각**, 시스템 지표는 **측정 시각**을 한국 시간으로 변환해 날짜를 정한다. 수집 시각과 이벤트 날짜가 달라도 해당 날짜로 인덱싱한다.
- 자정에 정확히 발생한 레코드는 다음 날짜에 속한다.
- 타임스탬프가 없는 로그는 날짜를 만들어 넣지 않는다. 수집일에 미배정 로그 건수로 표시하고 일일 이벤트 수에는 포함하지 않는다. 실제 발생일을 알아내려면 해당 서비스의 파서를 보강해야 한다.
- 레벨 미인식·인코딩 오류·수집 실패·필터 제외·커버리지 누락을 데이터 품질에 반영한다. 누락을 정상 상태로 해석하지 않는다.
- 오류 수준별 건수·HTTP 상태·명시적 응답 시간, 반복 오류와 제한된 대표 이벤트, 지표별 샘플 수·최소/최대/평균/최근값을 생성한다. 평균은 관측 샘플 평균이며 미관측 시간을 보간하지 않는다.
- 날짜별 배치 인덱스와 generation을 체크포인트 DB의 트랜잭션에서 함께 확정한다. 늦게 들어온 과거 날짜 이벤트도 그 날짜 generation을 증가시킨다.
- 새 배치는 `metrics.jsonl`에도 전체 관측 지표를 보관한다. 요약 크기 제한으로 지표가 잘려도 일일 집계에서 복원할 수 있다.

지연 로그가 저장되면 관련 기존 일일 보고서는 `stale: true`가 된다. 그 일일 보고서를 참조한 주간·월간도 갱신 필요 상태가 된다. 해당 daily를 다시 `run`한 뒤 weekly/monthly를 다시 `run`하면 새 하위 보고서를 참조한다. **자동 재분석·연쇄 작업 등록은 아직 없으며 이후 Worker/Airflow에서 연결한다.**

## 보고서 버전과 저장

동일 종류·기간·입력 fingerprint는 같은 보고서 버전을 재사용한다. fingerprint에는 입력 배치/하위 보고서 ID, 날짜 generation, 기대 수집 정책, 입력 크기 한도, 요청 모델과 분석 지침 해시가 포함된다. 같은 입력으로 이미 완료된 run을 다시 실행하면 Codex를 재호출하지 않는다.

입력이 바뀌면 같은 기간에 v0002, v0003처럼 새 버전을 만든다. 과거 버전과 결과는 그대로 남긴다. 실패한 동일 입력은 같은 버전으로 재시도하며 수집을 다시 할 필요가 없다.

```text
aiops_data/
├── collection/
│   ├── checkpoints.sqlite3          # 기존 체크포인트 + 날짜 인덱스
│   └── batches/batch-.../
│       ├── snapshot.json
│       ├── events.jsonl
│       └── metrics.jsonl            # 이번 변경 이후 새 배치부터
└── reports/
    ├── reports.sqlite3              # 로컬 보고서 원본 저장소
    ├── daily/2026-10-27/v0001/
    ├── weekly/2026-10-19/v0001/
    └── monthly/2026-10-01/v0001/
        ├── input.json
        ├── manifest.json
        ├── metadata.json
        └── result.json              # 분석 성공 시 생성
```

- `input.json`: Codex에 실제 제공한 제한된 입력. 기본 최대 90,000바이트와 AIOPS_MAX_INPUT_BYTES 중 작은 값.
- `manifest.json`: 전체 입력 배치/하위 보고서 ID와 버전·정책·generation. 입력의 일부 대표 정보가 잘려도 전체 의존 관계는 유지한다.
- `metadata.json`: 기간·버전·상태·커버리지·오류 코드.
- `result.json`: Provider의 작업 ID·Thread ID·요청 모델 및 검증된 분석 보고서.

SQLite가 보고서의 원본이며 JSON 파일은 조회/검토용 출력이다. 파일 출력 중 실패하면 DB에 저장된 입력·결과로 다음 실행에서 재출력한다. JSON을 수동 수정해도 다음 출력에서 덮어쓰므로 원본으로 편집하지 않는다. 파일 0644, 보고서 루트 0755을 사용한다. 백업 시 Collector·보고서 작업을 중지하고 `aiops_data/` 전체를 일관되게 보관한다. 자동 삭제는 하지 않는다.

보고서 ID 예: `daily-2026-10-27-v0001`. Provider job ID와는 별개다. weekly/monthly의 근거는 하위 `report_id`, daily의 근거는 입력에 실제 등장하는 event/metric ID다. 없는 근거 ID를 반환하면 분석 성공으로 저장하지 않는다.

출력의 `reused`는 기존 입력 버전 재사용 여부, `analysis_reused`는 완료된 분석 결과까지 재사용해 AI 호출을 생략했는지를 뜻한다. `report list`의 `stale`는 데이터/하위 보고서 의존 관계의 변화 여부다. 단순히 과거 버전이라는 이유만으로 stale로 표시하지는 않는다.

## 누락·실패·직렬화

일일 보고서가 없거나 최신 수집 데이터와 맞지 않으면 상위 분석에서 누락으로 표시한다. 하루가 누락되어도 확보된 다른 보고서로 부분 분석은 가능하며, 누락 날짜·오래된 보고서 ID·불완전한 일일 보고서 ID를 함께 제공한다. 월간은 가용한 주간 보고서가 없어도 일일 보고서를 기준으로 작성한다.

상태는 PREPARED → RUNNING → COMPLETED 또는 FAILED다. 보고서 상태와 데이터 완전성은 별개다. **COMPLETED + coverage_complete=false**는 불완전한 자료를 분석하는 데 성공했다는 뜻이다. 데이터가 전혀 없으면 prepare로 누락을 확인할 수 있지만 run은 AI를 호출하지 않고 설정/입력 오류를 반환한다.

- 0: 입력 준비/분석 성공이며 데이터 커버리지 조건 충족.
- 10: 입력/결과는 저장했지만 데이터 불완전.
- 나머지 2~9: 기존 설정·Provider 오류 코드 사용.
- `report list`: 정상 조회 시 0.

동일 데이터 루트의 보고서 작업은 보고서 잠금으로 직렬화하고, 실제 Codex는 기존 공통 codex.lock을 사용해 단발 analyze와도 동시 실행을 막는다. 보고서 AI 실행 동안 Collector 잠금은 해제하므로 새 수집은 계속할 수 있다. 실행 도중 추가된 지연 데이터는 다음 list/prepare에서 stale 여부로 확인한다.

프로세스 중단으로 남은 RUNNING은 다음 보고서 명령에서 FAILED/interrupted로 바꾸고 명시적 재실행할 수 있다. 이것은 분산 큐나 상시 Worker의 자동 복구 구현을 의미하지 않는다.

## 기존 데이터와 이후 연결

기존 checkpoints.sqlite3를 지우지 않는다. 날짜 인덱스 테이블은 자동 추가되고, 첫 보고서 명령에서 기존 배치를 한 번 인덱싱한다. 읽기량은 보관된 배치 전체에 비례하므로 첫 실행이 더 걸릴 수 있다. 원본 서비스 로그는 다시 읽지 않는다. 기존 배치의 이벤트만으로 알려진 시각을 사용하며 원본 파싱을 소급 수정하지 않는다.

이전 배치에 metrics.jsonl이 없으면 snapshot.json에 남은 지표만 사용하고 legacy_metrics_batches를 기록한다. 이전 요약에서 생략된 지표·수집 이전 이력·해석 불가능한 시각은 새 기능만으로 복원할 수 없다. 운영에서 이미 확인한 파서 미인식·수집 한도 문제는 별도로 보완해야 한다.

기본 로컬 SQLite 보고서 카탈로그와 선택적 PostgreSQL 저장소가 같은 기간·버전·의존 관계 계약을 사용한다. 검증 결과는 [REPORTING_VALIDATION.md](REPORTING_VALIDATION.md)에 기록한다. PostgreSQL 저장소·작업 큐/단일 Worker는 구현했으며 FastAPI(9023) 조회·Airflow DAG는 이후 연결한다. 프론트 추가 시 기본 포트는 4003이다. 운영 DB 변경이나 스케줄 설치는 이번 변경에 포함하지 않는다.

예정 스케줄 예시는 5분 수집, 매일 00:15 전날 분석, 월요일 01:00 지난주 분석, 매월 1일 02:00 지난달 분석이다. 실제 실행 시각보다 **하위 보고서 완료 의존성**을 우선한다. 장애·사용량 제한으로 일일 분석이 밀리면 상위 작업은 누락을 표시하거나 기다렸다가 재시도해야 한다. 지연 도착 재분석 범위와 자동 재처리 주기는 Worker/DAG 도입 시 정한다.

## 일일 점검의 장애·성능 분석

일일 보고서 한 건 안에 종합 요약/발견 사항과 `incident_analysis`, `performance_analysis`를 함께 저장한다. 별도 보고서 종류·큐 작업·Codex 호출을 추가하지 않는다. 기존 POST /v1/reports의 type=daily와 Worker 1회 호출을 그대로 사용한다.

- 장애 분석: 오류 발생 시각과 반복 패턴, 관련 서비스, 원인 후보, 영향 범위와 복구 근거를 구분한다. 자료가 없는 원인·영향·복구 완료를 단정하지 않는다.
- 성능 분석: 관측된 자원 지표의 최소/최대/평균/표본 수, 측정된 HTTP 지연과 명시적인 지연 로그를 분석한다. 기준값·분위수·시간당 처리량·추세·DB 대기·Kafka lag를 임의로 만들지 않는다. 표본 하나로 추세를 판단하지 않는다.
- 구역 상태: ISSUES_OBSERVED(근거 있는 문제 관측), NO_ISSUES_OBSERVED(수집 범위와 관련 관측 근거가 충분한 경우만), INSUFFICIENT_DATA(신뢰할 판단 근거 부족). 근거 부족은 정상 판정이 아니다. 각 구역에는 summary/findings/limitations를 기록하고 발견 사항마다 실제 입력의 근거 ID를 요구한다.

입력 계약은 3이다. 서비스별 오류 그룹을 균형 있게 선정하고, 대표 이벤트에서는 높은 심각도의 로그와 측정 지연 표본을 보존한다. 입력 제한에 걸리면 특정 서비스의 상세를 뒤에서 전부 지우는 대신 중복 대표 정보를 먼저 줄인다. 지표 요약은 로그 상세보다 나중에 축소하며, 한계를 명시한다. 전체 로그가 모델에 전달되는 것은 아니다.

완료된 기존 보고서는 수정하지 않는다. 이전 형식은 새 구역이 없는 상태로 조회되며, 다음 일일 분석부터 새 구역이 채워진다. 같은 기간을 다시 요청하면 변경된 분석 정책으로 새 수정본을 만든다. 배포 전에 준비한 대기 작업은 기존 정책 해시가 달라 stale_input으로 취소될 수 있으므로 해당 기간을 다시 요청한다. 주간·월간 입력에는 새 구역의 상태와 요약을 함께 전달하며 기존 일일 보고서도 계속 입력으로 사용할 수 있다. DB 스키마 변경은 없다.
