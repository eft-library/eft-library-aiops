# Phase 1 — 프로젝트 기반 및 Codex 연동

## 1. 목표
로컬에서 Python 기반 `eft-library-aiops` 프로젝트를 개발하고, 공식 Codex 실행 인터페이스를 통해 **샘플 데이터의 읽기 전용 분석**을 수행한다. Phase 1에서는 운영 로그 수집·운영 DB 변경·운영 Airflow 배포를 하지 않는다.

## 1.1 전체 프로젝트 목적과 개발 흐름
EFT Library의 서비스 로그와 시스템 상태를 수집·정제하고, Codex가 장애 원인과 개선 방향을 근거와 함께 제안하는 운영 분석 시스템을 만든다. 자동 수정·서비스 재시작·배포는 범위에 포함하지 않는다.

```text
Phase 1: Python CLI + Codex Provider + 샘플 분석
Phase 2: 로그·시스템 상태 수집 → 정규화·마스킹·집계 → JSON 배치 저장
Phase 3: 분석 작업 관리 → 단일 Codex 실행 → 결과 검증 → PostgreSQL 저장
운영 검증: 개발 완료 후 배포 → 실제 경로·권한·인증·자원·Airflow 연동 확인
```

- Phase 1~3 구현과 로컬 검증을 순차적으로 완료한 뒤 운영 서버에 배포해 통합 테스트한다. 각 단계 완료에 운영 서버 접근을 요구하지 않는다.
- 로그 수집·전처리는 AI 없이 동작하며, AI 분석 실패 시에도 저장된 배치를 재분석할 수 있어야 한다.
- 전체 로그 대신 필요한 집계와 대표 로그만 AI에 전달한다. 향후 다른 Provider를 추가할 수 있도록 분석 정책과 호출 구현을 분리한다.
- 불필요한 상시 프로세스와 프레임워크는 도입하지 않는다. API·웹 UI·자동 복구는 현재 필수 산출물이 아니다.
- 이 문서와 PHASE2.md, PHASE3.md를 개발 요구사항의 기준으로 사용한다.

## 2. 환경 및 제약
- 개발 환경: 현재 로컬 환경. 운영 경로·Linux 계정·Docker 접근이 존재한다고 가정하지 않고 샘플과 테스트 대역으로 개발한다.
- 배포 대상: Rocky Linux 10.1, CPU 12 logical, RAM 32GB, Swap 15GB. 운영 자원 여유는 배포 시 다시 측정한다.
- Python: 3.12 기준으로 시작하되 로컬 설치 버전과 운영 대상 버전, 공식 지원 범위를 검증한다. 장기적으로 3.14 전환을 고려한다.
- 패키지 관리: `uv`; 테스트: `pytest`; 설정: 환경변수 + 예제 파일.
- AI: OpenAI Codex. **공식 Python SDK의 존재·설치명·API·인증 지원 여부를 공식 문서에서 먼저 검증한다.** 불명확하거나 요구 기능을 지원하지 않으면 CLI(`codex exec`)를 Python subprocess로 호출하는 대안을 비교·제안한다. 가상의 SDK 메서드를 구현하지 않는다.
- 인증: 사용자의 ChatGPT 로그인 우선 검토. SDK와 CLI의 인증 재사용 가능 여부, 플랜 사용량 제한, API 키 사용 시 별도 과금 여부를 확인한다.
- 동시 Codex 실행: 1개. 초기 타임아웃 10분. Codex가 접근하는 작업 공간은 별도 디렉터리로 제한한다.
- 운영 서버의 서비스 재시작, 파일 수정·삭제, DB 스키마 변경, 방화벽 변경 금지.

## 3. 범위
1. Python 프로젝트 초기화 및 `pyproject.toml`, `uv.lock` 생성.
2. 프로젝트 구성: `src/aiops/`, `tests/`, `config/`, `prompts/`, `docs/`.
3. Codex Provider 인터페이스 설계(실행, 결과, 오류, 세션/스레드 ID, 가능하다면 진행 이벤트).
4. 검증된 공식 API 또는 CLI 기반 어댑터 구현. `read-only` 및 승인 정책을 확인하고 운영 배포 시 적용할 별도 Linux 계정/파일 권한 격리를 문서화한다. 로컬에서는 임시 작업 디렉터리와 샘플로 검증한다.
5. `aiops doctor`(환경/인증 상태 점검), `aiops analyze --input <sample>`(샘플 분석) 등 최소 CLI.
6. 시간 제한, 예외·종료 코드 처리, 민감정보가 포함되지 않은 실행 메타데이터 기록.
7. 테스트용 **가짜 Provider**를 사용한 단위 테스트. 실 Codex 호출은 명시적 opt-in 테스트로 분리.
8. `.env.example`, `.gitignore`, README, 실행 방법 및 운영 보안 문서.

## 5. 안전 요구사항
- 운영 서버 루트 권한으로 Agent를 실행하지 않는다. 별도 최소 권한 계정 사용을 문서화한다.
- Codex에는 Phase 1의 샘플 파일만 제공한다. 서버 전체 경로·비밀 파일·운영 설정은 분석 대상에서 제외한다.
- 토큰·인증 파일·세션 데이터·로그 원문을 Git에 커밋하지 않는다.
- 타임아웃 시 하위 프로세스까지 정리되는지 검증한다.
- 읽기 전용 샌드박스가 모든 OS 접근을 보장하지 않으므로 파일 권한과 실행 경로 제한을 병행한다.

## 6. 검증 및 완료 기준
- `uv sync`와 단위 테스트가 통과한다.
- 인증 미설정, 네트워크 실패, 사용량 제한, 시간 초과에 대한 오류가 구분된다.
- 샘플 데이터로 단일 분석을 실행하고 결과 및 작업 식별자를 출력한다.
- 실제 Codex 호출 없이도 대부분의 테스트를 실행할 수 있다.
- 테스트는 샘플과 임시 디렉터리만 사용하며 기존 서비스·설정·데이터를 변경하지 않는다.
- 로컬 개발 완료와 운영 호환성 검증 대기 항목을 구분해 기록한다. Linux 권한 격리와 운영 자원 제한의 실효성은 배포 후 검증한다.

## 7. Codex에 전달할 작업 지시
> Phase 1만 로컬에서 구현하라. 운영 서버 접근을 완료 조건으로 삼지 말고 샘플·가짜 Provider로 검증하라. 먼저 공식 Codex Python SDK의 현재 지원 상태·인증 방식·실제 API를 확인하고, 사용 불가능한 부분은 근거와 함께 CLI 대안으로 제시하라. 기존 운영 서비스에는 어떤 변경도 하지 말고, 생성한 파일·실행한 테스트·남은 위험을 보고하라.
