# 일일 심화 조사와 대응 가이드

일일 분석이 끝난 뒤 별도 API로 접수하는 두 번째 단계다. 기존 일일 보고서를 보존하고, 현재 관측 결과와 운영자용 원인 확인·대응 절차를 연결해서 저장한다. 자동 복구·재시작·설정 변경은 실행하지 않는다.

## 운영 반영

이번 기능은 **마이그레이션 3**이 필요하다. 기존 데이터베이스를 삭제하거나 다시 만들지 않는다. 기존 `.env`와 수집 설정을 유지한 채 다음을 실행한다.

```sh
./scripts/init.sh
./restart.sh
uv run aiops --env-file .env db doctor
```

점검 결과는 `schema: public`, `migration: 3`이다. `public.aiops_investigations`와 `public.aiops_investigation_attempts`를 추가한다. 기존 보고서·작업 큐 테이블의 데이터는 변경하지 않는다. 일반 API 호출은 자동 마이그레이션하지 않는다. 마이그레이션 2만 있는 환경에서도 기존 보고서 조회는 유지되지만 새 조사 접수에는 먼저 초기화가 필요하다.

추가 비밀키나 Codex 로그인은 필요 없다. 기존 API 인증·Codex 인증·`AIOPS_MODEL`을 사용한다. 수집 소스·시스템·Docker 대상은 API 실행 시 지정한 수집 설정을 사용한다. 실제 주소·경로·계정은 Git 문서에 기록하지 않는다.

## Airflow 연결: 일일 DAG에만 추가

```text
기존 일일 분석 COMPLETED 확인
  → 조사 접수(report_id)
  → 조사 Worker 한 건 실행(investigation_id)
  → 조사 상태 조회
  → COMPLETED / FAILED / TIMEOUT 판단
```

DAG 구현은 별도 Airflow 프로젝트에서 수행한다. 주간·월간 DAG는 변경하지 않는다. 일반 보고서 Worker와 조사 Worker는 서로 다른 큐를 처리하지만 같은 PostgreSQL Worker 잠금을 사용하므로 동시에 실행되지 않는다.

모든 호출에는 기존 `X-AIOps-Key` 헤더가 필요하다.

### 1. 접수

`POST /v1/investigations`

```json
{"report_id":"daily-2026-10-29-v0001","request_key":"default"}
```

HTTP 202와 `investigation_id`, 같은 값의 `job_id`, `report_id`, `status`, 시도 횟수·시각을 반환한다. 완료된 **일일 보고서의 정확한 수정본 ID**만 받는다. 주간·월간·없는 보고서·미완료 보고서는 422다. 일일 분석 접수의 202만 보고 조사하지 말고 먼저 일일 작업의 COMPLETED를 확인한다.

같은 `report_id`와 `request_key`는 같은 조사 이력을 반환하며 재실행하지 않는다. Airflow 재시도는 같은 키를 유지한다. 다른 시각에 새 관측을 하거나 최종 실패 후 다시 조사하려면 운영자가 새 키를 지정한다. 과거 이력은 보존한다. 모델은 최초 접수 시 고정한다.

### 2. Worker 실행

`POST /v1/investigations/worker/run-once`

```json
{"investigation_id":"<INVESTIGATION_UUID>"}
```

지정한 조사만 한 건 처리한다. `{}`를 보내면 실행 가능한 조사 중 가장 먼저 접수한 한 건을 처리한다. **기존 `/v1/worker/run-once`는 일일·주간·월간 보고서 큐만 처리하며 조사 큐를 처리하지 않는다.**

이번 조사 Worker API는 동기 JSON 응답이다. 기존 보고서 SSE API와 별개이며 조사 진행 메시지 스트리밍은 제공하지 않는다. Airflow HTTP timeout은 조회 시간과 기존 `AIOPS_TIMEOUT_SECONDS`를 합친 시간보다 여유 있게 설정한다. 요청이 끊겨도 접수 ID를 버리지 말고 상태를 먼저 조회한다.

다른 보고서/조사 Worker가 실행 중이면 409다. 준비된 대상이 없거나 재시도 대기 시각 전이면 `{"status":"idle"}`을 반환한다. idle을 조사 완료로 간주하지 않는다.

### 3. 상태·결과 확인

`GET /v1/investigations/<INVESTIGATION_UUID>`

- `PENDING`: 실행 대기 또는 재시도 예약. `available_at` 이후 Worker를 다시 호출한다.
- `RUNNING`: 처리 중. 상태를 조회한다. 일일 보고서 상태와 별개다.
- `COMPLETED`: 구조화된 결과 검증과 저장 완료. 실제 운영 변경·원인 확정을 뜻하지 않는다.
- `FAILED`, `TIMEOUT`: 최종 실패. `error`를 확인한다. 자동으로 새 조사 키를 만들며 무한 재시도하지 않는다.

네트워크·시간 초과·실행 오류·중단은 최대 3회, 30초·60초 간격으로 재시도한다. 인증·사용량 제한·입력/출력 오류는 자동 재시도하지 않는다. Codex 잠금 충돌은 실제 분석 시도로 계산하지 않고 5초 후 다시 대기한다. Worker가 중단되어 RUNNING으로 남은 작업은 다음 조사 Worker 호출에서 복구한다. HTTP 성공 여부뿐 아니라 응답의 상태를 판단한다. 기본 보고서는 조사 실패의 영향을 받지 않는다.

## 자동 조회 범위

입력에는 프로젝트의 서비스 역할·의존 관계를 설명하는 아키텍처 참고 정보도 포함한다. 이는 실제 프로세스 상태나 연결 성공을 확인한 증거가 아니며 배포 식별자는 별도 확인한다.

AIOps가 아래 고정 조회를 수행하고 마스킹한 결과만 Codex에 전달한다. 모델이 만든 명령·SQL을 실행하는 기능은 없다. 수집 체크포인트도 갱신하지 않는다.

| 조회 | 범위와 제한 |
| --- | --- |
| 시스템 | 설정에서 켠 CPU·메모리·swap·load·디스크의 현재 표본 |
| 로그 | 활성 소스별 최대 256개 항목·1초 탐색 범위 중 최근 파일 하나의 마지막 8KiB. 모델에 전달할 문자열은 추가로 제한·마스킹 |
| Docker | 설정에서 켠 명시적 컨테이너의 상태·자원 지표. subprocess 최대 10초. stdout·환경변수·inspect·exec 제외 |
| PostgreSQL | 설정된 **AIOps DB**의 누적 통계, 세션 상태/대기 유형 집계, 대기 잠금 수. read-only 트랜잭션·2초 statement timeout. 쿼리 본문·사용자·클라이언트 주소 제외 |

심볼릭 링크와 일반 파일이 아닌 대상을 읽지 않는다. API에서 임의 경로·명령·DB 접속값·조회 URL을 받지 않는다. 조회 불가·권한 부족·잘린 입력은 정상으로 해석하지 않는다. 결과 입력은 최대 90KB 또는 설정된 더 작은 입력 한도로 제한하고, 조사 결과는 최대 150KB로 제한한다.

AIOps DB 통계는 별도 애플리케이션 DB의 상태를 보장하지 않는다. Redis 런타임 통계·Kafka lag·서비스별 연결 풀·과거 지표를 임의 접속으로 가져오지 않는다. 해당 근거가 없으면 한계와 운영자 추가 확인 절차에 남긴다. 처음 제공되는 조사 입력·결과는 기존 로그 마스킹과 마찬가지로 운영자가 검토한다.

## 결과와 화면

`input`에 원본 일일 보고서 참조·대상 기간·현재 관측 목록·조회 시각·제한을 저장하고 `result.report`에 다음을 저장한다.

- 당시 증거, 조사 시점의 관측, 현재 판단과 남은 가설
- 원인 확인 순서: 목적·읽기 전용 명령 또는 SQL 예시·결과 해석·다음 확인
- 대응 제안: 조치·적용 조건·위험과 영향·복구 확인·되돌리기
- 재발 시 확보할 자료, 근거 ID와 조사 한계

명령의 `<SERVICE>`, `<DB_HOST>`, `<LOG_PATH>` 등은 배포 환경에서 확인한 값으로 바꿔 검토한다. 웹에서 명령 실행·복사 후 자동 적용 기능은 제공하지 않는다. 현재 상태가 정상이어도 어제 원인이 증명되거나 복구되었다고 단정하지 않는다.

조회 웹의 일일 보고서 상세에 **심화 조사 · 대응 가이드**가 표시된다. 최근 조사 5개의 상태·시각·결과와 관측 근거를 확인할 수 있다. 전체 개별 이력은 조사 ID로 API에서 조회한다. 기존 보고서에 조사 이력이 없어도 정상 표시한다.

주간·월간 입력에는 각 일일 보고서에 연결된 **최근 완료 조사 요약**을 포함한다. 새로운 운영 조회나 추가 조사 작업은 실행하지 않는다. 참조한 조사 ID는 manifest에 보존하며 조사 결과가 추가되면 기존 상위 보고서를 stale로 판단해 새 수정본 생성에 반영한다. 기존 상위 보고서는 자동으로 다시 실행하지 않는다. 조사 요약도 입력 크기 한도에 따라 축약될 수 있다.
